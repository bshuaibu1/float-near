every session. If you are about to suggest something in a Rejected cell, read the Why first

## Contract architecture

| Date | Chose | Rejected | Why |
|---|---|---|---|
| 2026-11-09 | Top-up is a **CLI that signs** plus a **read-only tool that quotes** (`vault_gas`) | A `vault_plan_topup` returning a signable payload, like every other owner action | A top-up is `transferToGasKey`, an action on the VAULT account needing a full-access key OF the vault. Wallets **ignore `signerId`** and sign as the connected account while returning SUCCESS (Meteor, Intear, CLI connector alike, measured 2026-11-07) — so a "plan" here would hand the user a payload their wallet silently signs as the WRONG account. There is no payload that can work, so the honest split is: the agent does the arithmetic and the reading, a human runs the signing. Same shape as `vault_teardown_report`. |
| 2026-11-09 | **Mirror** the gas arithmetic into mcp, and fail the gate on drift | Importing it across packages; or duplicating without a check | create-float and mcp are siblings published separately and installed independently, so a dependency either way couples two release cycles — and a `^0.3.0` range that silently resolved to a PUBLISHED sibling instead of the local one already cost an afternoon and broke the first VPS deploy. Follows the existing `shared/contract-constants.json` pattern. The check COMPUTES with both copies over 63 cases rather than grepping for a literal, because a regex can match a constant nothing uses. Drift matters here specifically: the MCP **quotes** a top-up and the CLI **charges** for it, so divergence tells a user one number and bills another, with both halves looking right alone. |
| 2026-11-09 | **One NEP-611 gas key PER AGENT**, funded 0.12 at creation or >= `MIN_AGENT_GAS_FUNDING` 0.06 via `add_role` | A single CENTRAL gas key shared by every agent, to save the per-agent float | **The key IS the agent's identity**, so this is not a cost trade — it deletes the product. `pubkey_to_node: LookupMap<PublicKey, NodeId>` (lib.rs:195) and `request_payment` resolves the caller's node with `env::signer_account_pk()` (lib.rs:1297). One shared key maps every agent to ONE node: one shared daily budget, no hierarchy, no `PARENT_DAILY_BUDGET` vs `DAILY_BUDGET` — i.e. exactly SpactVault's limitation, which is differentiator #1. Second-order: a shared key is a shared rate limit, so one runaway agent starves the rest, whereas a per-agent balance is a bound NEAR enforces for free (`allowance: null`, the BALANCE is the cap). The float is small and refundable: 0.000674/payment measured, so 0.12 funds ~178 payments. |
| 2026-10-28 | `Route` = `NearDirect` \| `Intents` | The MPC / Base rail (Chain Signatures) | Vault-signed **delivery** was never proven. A signature is authority, not delivery. `KNOWN-TRADEOFFS.md` §3/5/6 kept as historical record — the chain measurements can't be reconstructed. |
| ~2026-11 | **Virtual agents** (`bind_virtual_agent`, ~168 B / ~0.0017 NEAR) + a NEP-611 gas key on the vault | Real sub-accounts at 0.55 NEAR each (`create_agent_account`, now removed) | Every agent ever created **stranded its funding permanently** — a function-call key cannot sign `DeleteAccount` and NEAR requires `actor_id == account_id`. Measured loss: **10.7752 NEAR across 18 testnet agents + 0.54434 mainnet, unrecoverable by anyone, forever.** `bind_agent` deliberately kept (binds an existing account → strands nothing). |
| — | `MAX_DEPTH` 3 → 4 | Keeping 3 | So `root → team → agent → sub-agent` is expressible. Costs ~3 map reads + 1 write per payment and stays a **fixed-length** walk — that is the property that matters. |
| — | Owner-mediated delegation | `spawn_child` (agent-initiated sub-agents) | An agent's key can't attach a deposit, and widening it hands the agent the vault's transfer authority. Still *possible* now `remove_node` reclaims slots, but needs a per-node quota and a funding source that isn't "the vault, on an agent's say-so". |
| — | `remove_node` **strict**: frozen + childless + non-root + no open reservations across **today *and* yesterday** | A simple delete | A reservation taken before midnight is still open after it; checking only today misses exactly that case. |
| — | Ledgers are **NOT** deleted on `remove_node` | Deleting them to reclaim storage | A surviving reservation releasing via `pending.checked_sub` against a resurrected-as-zero ledger would **underflow and panic inside a callback**, stranding the reservation at every level. Ids are never reused, so the rows are inert. |
| 2026-10-29 | Two-step `propose_owner` / `accept_ownership` | One-shot `set_owner` | A typo would hand the vault to a nonexistent string instantly and irreversibly. |
| 2026-10-29 | `withdraw` sits **outside** the budget hierarchy and is **not** gated on `paused` | Applying caps to the owner's own exit | Caps bound what *agents* spend. Applying them to the owner created a 100-day drip for a 10,000 USDC deposit. **"An escape hatch a pause can close is not an escape hatch."** |
| — | `sweep_stuck_pending` age floor is a **constant** (1 h) | An owner-supplied age | An owner who could pass zero could release a live reservation whose callback was about to land. Tagged `SWEPT_STUCK`, never `TRANSFER_FAILED`, so an audit can tell intervention from rail failure. |
| — | Blocked payments returned as a value + NEP-297 event, **never stored** | Persisting refusals on-chain | Storing them is the storage-griefing vector — an agent could inflate the vault's storage bill by spamming rejects. Accepted cost: refusals are invisible to anything not watching, which is *why* the follower/scanner exists. |
| 2026-10-31 | Approval gate stored under **raw keys**, not a `Vault` field; **nothing reserved** while a ticket waits; the **lowest** threshold in the chain binds | A struct field; reserving on hold | Raw keys ⇒ **no borsh migration**, live vault upgradeable in place. Not reserving ⇒ a held payment doesn't block other spending, an approval can't slip past a cap tightened while waiting, and a stale Intents quote is refused at approval with `QUOTE_EXPIRED`. Deliberately *unlike* `effective_recipients`, where a child list **replaces** an inherited one. |
| — | Fixed daily window (`block_timestamp / day_len_ns`); the midnight cliff is **accepted** | Rolling 24 h | Fixed window is what makes the hot path O(1) — one ledger key per `(node, token, day)`, no history to scan. `per_tx_cap` + `cooldown_sec` bound the burst to ≤2× daily cap. |
| — | **Hierarchical** cooldown (`PARENT_COOLDOWN`) | Leaf-only cooldown | "Like every other check." A mutation reverting the chain-wide `last_paid_ns` write to leaf-only is F3's fix undone, and is now caught. |
| — | Vault-wide NEAR budget (`DEFAULT_MAX_DAILY_NEAR = 10 millinear`) | No NEAR cap | F2: an agent could drain the vault's NEAR, which no token cap governed. |
| 2026-10-31 | **The vault registers the Intents deposit address itself** | An operator daemon | Two independent killers: **ordering** (the daemon learns the address only once the transfer is already in flight, same transaction) and **authority** (`storage_deposit` needs an attached deposit ⇒ a FULL-ACCESS key in a long-running network service). |
| — | `add_role` authorises by **DEPOSIT**, not `assert_owner` | `assert_owner()` (exactly 1 yocto) | The gas key needs real funding, and a function-call key **cannot attach a deposit at all** — so an attached balance *proves* a full-access/wallet signature. New role nodes are children of root deliberately, so adding a 10th agent **divides** the daily loss rather than raising it. |
| — | `MIN_AGENT_KEY_ALLOWANCE` floor **not** lowered | Shaving it to save testnet tokens | The allowance **is** the per-agent rate limit NEAR enforces for free. Shaving it quietly undercuts the anti-griefing argument. |
| — | `LEDGER_INVARIANT` deliberately **untested** | Writing a test for it | Unreachable by any public call sequence; "contriving it would assert the contrivance." |
